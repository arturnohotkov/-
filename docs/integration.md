# Архітектура, API та карта інтеграції

## Два варіанти розгортання

Браузер отримує статичні HTML, CSS і JavaScript із того самого джерела, що й HTTP API. Далі запит проходить через перевірку ролі, доменну операцію та адаптер зберігання. Вебсторінка, звіт і експорт використовують спільний розрахунок у core/model.mjs. Для роботи інтерфейсу не потрібні зовнішні шрифти, аналітика або генеративний сервіс.

| Варіант | Дані | Призначення |
|---|---|---|
| Хостинговий прототип | D1, окремий демопростір на сесію відвідувача | Демонстраційний інтерфейс, спільні одноразові посилання в межах простору |
| Автономний Node.js | Локальний SQLite у VECTOR_DATA або .local-data | Запуск без зовнішньої хмари. Режим demo за замовчуванням, team для спільної модельної установи |

Операції з одним простором записуються атомарно з порівнянням ревізії. У разі паралельної модифікації API повертає HTTP 409, клієнт може повторити операцію. Для конкурсного обсягу агрегати, статуси, ролі та журнал одного простору зберігаються в одному записі. Для великої кількості установ і тривалого архіву доцільно рознести цикли, агрегати та журнал у версіоновані таблиці й додати посторінкову вибірку.

## Локальне розгортання як модуль

1. У середовищі процесу установіть VECTOR_MODE=team, окремі випадкові значення VECTOR_LEAD_KEY і VECTOR_OFFICER_KEY та каталог VECTOR_DATA. Приклад переліку змінних є в .env.example.
2. Запустіть node offline/server.mjs. За замовчуванням сервер слухає лише 127.0.0.1:4173. За HTTPS-проксі задайте VECTOR_ORIGIN рівним зовнішній адресі сервісу. Задайте HOST та PORT згідно з конфігурацією локального контуру. Базове налаштування розраховано на окреме ім’я вузла.
3. Відкрийте сервіс з локального порталу установи. У режимі team перемикач деморолей відсутній. Керівник і уповноважений входять окремо, учасник отримує одноразове посилання. Сервер працює з синтетичними даними й у цьому режимі.

## Реалізований контракт, префікс /api/v1/

Сесія управлінської ролі передається HttpOnly cookie. POST приймає JSON. Відповіді стану та звіту не кешуються. Для закритого розгортання трафік із порталу повинен йти через довірений шлюз з установленим публічним origin.

| Метод і маршрут | Призначення | Доступ |
|---|---|---|
| POST start, POST role | Старт демопростору, зміна демонстраційної ролі | Власник демопростору |
| POST login | Вхід з полями role та code | Автономний режим team |
| GET state | Захищена за роллю проєкція циклів, даних і заходів | Поточна роль |
| POST cycle | Створення циклу з name та k, де 5 ≤ k ≤ 50 | Уповноважений |
| POST issue | Одноразове запрошення за cycle та group | Уповноважений, у персональній демонстрації також її власник |
| POST invite-info, POST answer | Форма й одноразове надсилання. для запрошення з version=2 поле answers містить 12 значень 0…4 або null у порядку questions з invite-info. Для раніше виданих запрошень підтримується 3 значення | Володілець запрошення |
| POST inputs | Експертні оцінки expert[3] та документи facts[3] з полями a, b | Уповноважений |
| POST confirm, POST close | Підтвердження джерел, фіксація підсумків | Керівник |
| POST measure | Прийняття рекомендації. Поля cycle, criterion, text, owner, due | Керівник |
| POST status | Зміна стану заходу за id та status | Керівник або уповноважений |
| GET report.csv?cycle=5 | Готовий CSV у кодуванні UTF-8 | Керівник або уповноважений |

У цілях масштабування профіль критеріїв містить опис адаптованого питання, варіанти відповіді, документальний знаменник, посилання на першоджерело й відповідну дію. Тип установи або трійку критеріїв можна адаптувати у коді. Розширення кількості компонентів потребує оновити валідацію, перевірки та версію методики. Зіставляти індекси різних профілів можна лише після перевірки порівнянності.

## Карта можливих інтеграцій

| Система-кандидат | Що обмінюється | Де проходить межа |
|---|---|---|
| Moodle ВІКНУ або інша LMS ВВНЗ | На рівні циклу — агреговані чисельник/знаменник охоплення навчанням. За потреби портал відкриває відокремлену сторінку опитування | Адаптер власника LMS формує агрегат із дозволеного звіту. Персональні навчальні записи лишаються у LMS. Для порівняння з охопленням потрібна узгоджена версія критерію |
| Відомча система електронного документообігу конкретного закладу | Затверджений PDF/CSV і реквізити рішення. У відповідь — статус реєстрації документа | В MVP працює ручна передача файла. Автоматичний адаптер, перевірку доступів та облік версій погоджують із власником СЕД |
| Єдиний портал повідомлень викривачів НАЗК | Прототип оцінює обізнаність щодо каналу. Можливе довідкове посилання на офіційний ресурс та підтверджений інституційний факт готовності | Зміст звернень, особи викривачів і матеріали розгляду до аналітичної системи не передаються. Пропозиція не передбачає читання бази порталу |
| Внутрішній сервіс контролю виконання заходів | Прийнятий захід, відповідальний підрозділ, строк, статус і наступний агрегований показник | Діючий MVP веде власний трекер. Для системного обміну потрібні службовий доступ, зіставлення ідентифікаторів і запобігання повторному створенню заходу |

У прототипі реалізовано власний API та експорт. Промислові з’єднання з названими системами не встановлювалися.
